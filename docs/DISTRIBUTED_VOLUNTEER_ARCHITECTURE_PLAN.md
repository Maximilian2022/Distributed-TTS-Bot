- **作成日**: 2026-10-22
- **ステータス**: 承認済み（基本合意完了・移行完了後にKick予定）
- **対象環境**: `ttsbot` / `ttsbot-oss` 新環境

---

## 1. ビジョンと背景

### コンセプト
「導入された各Discordサーバーのメンバーが、自分のPCや余剰マシン（Node）を少しずつ持ち寄って巨大な音声合成ネットワークを構築する」コミュニティ協調型TTSシステム。

### 従来の課題
1. 1台のマシンに VOICEVOX / COEIROINK / AivisSpeech などの重量級TTSエンジンをすべて相乗りさせると、VRAM・CPUリソースが逼迫する。
2. 自宅LAN内の固定IP/SSHを前提としており、外部ユーザーの参加やルーターのNAT越え・ポート開放が困難。
3. Masterが単一拠点に依存しており、回線切断やサーバー障害で全体が停止する。

### 新アーキテクチャがもたらす価値
- **マシンスペックの最適化**: 各ユーザーが持っているエンジン（例: AさんはVOICEVOX、BさんはCOEIROINK）だけを担当し、負荷を分散。
- **コミュニティ貢献感**: 「自分のPCがサーバーの読み上げを支えている」という連帯感と、専用枠による優先処理。
- **マルチクラウドHA**: MasterをGCP/OCI等の複数拠点に分散し、高可用性を低コストで担保。

## 2. アーキテクチャ概要

```text
  ┌──────────────────────────────────────────────────────────────┐
  │                 クラウド側 (Active-Standby HA)               │
  │                                                              │
  │   [GCP Compute]                  [OCI Always Free]           │
  │    Master (Active)  <───互監視───>  Master (Standby)           │
  │       │                               ▲                      │
  │       ├─────── Redis / PostgreSQL ────┤ (状態・設定の共通同期) │
  │       │       (分散ロック・Leader選出)  │                      │
  │       ▼                                                      │
  │   Discord Gateway / VC接続 (常に1箇所のみアクティブ)           │
  │   Worker WebSocket Gateway (/ws/worker)                      │
  └───────────────▲──────────────────────────────▲───────────────┘
                  │                              │ (クライアントフェイルオーバー)
  ════════════════╪══════════════════════════════╪════════════════
                  │ 外向き WebSocket (WSS)        │ ポート開放・NAT設定不要
  ┌───────────────┴──────────────────────────────┴───────────────┐
  │                 各ユーザーの分散 Worker ノード               │
  │                                                              │
  │  【ユーザーA: Windows (Native)】  【ユーザーB: Windows (Docker)】│
  │   - トレイ常駐 / ゲーム自動ポーズ   - Docker Compose バックグラウンド│
  │   - VOICEVOX 担当                 - COEIROINK 担当             │
  │   - サーバーA 専用枠              - 全体共有プール             │
  │                                                              │
  │  【ユーザーC: Linux (systemd)】   【クラウド/ローカル (自前)】 │
  │   - AivisSpeech 担当              - Google TTS / OpenJTalk   │
  │                                     (ノード離脱時の最終防衛線) │
  └──────────────────────────────────────────────────────────────┘
```

## 3. コンポーネント別詳細設計

### 3.1 Master層 (オーケストレータ & Gateway)
- **Active-Standby HA (スプリットブレイン防止)**:
  - 共通の自前 Redis サーバーに `ttsbot:leader:master` を TTL 10秒 でハートビート登録。
  - ロックを獲得した Master のみが Active となり、Discord Gateway 接続および VC 接続を保持。
  - Standby 側は接続を切断した状態で待機し、Active のハートビート途絶時に自律昇格。
- **データ同期 (PostgreSQL)**:
  - ギルド設定、単語辞書、NGワード、ノード登録情報 (`nodes` テーブル) を一元管理。
- **Worker WebSocket Gateway (`/ws/worker`)**:
  - 外向き WSS 接続を受け入れ、ノード発行トークン（Bearer）で認証。
  - ハンドシェイク時に Capabilities（保持エンジン、対応話者UUID一覧、GPUスペック）を受信・登録。
  - 5秒おきの Ping/Pong による死活監視と回線 RTT 計測。

### 3.2 音響・ストリーミングパイプライン（レイテンシ隠蔽）
一般家庭の回線遅延・一時的な混雑を前提とし、以下の多段パイプラインで超低遅延を死守：
1. **句読点なしチャット対応・多段チャンキング（30文字ハードキャップ安全スライス）**:
   - チャット文化（句読点を打たない短文連投・スペース区切り・口語表現）に特化し、以下の多段ルールで自然に分割：
     - **① スペース（空白）境界分割**: 全角・半角スペースを読点（、）相当の文境界として扱う（英単語間の空白は保護。ポーズ: 60〜80ms）。
     - **② スラング・絵文字・笑い境界**: `w`、`草`、拍手（`888`）、絵文字の直後を分割トリガーとし、前後の文脈を分離。
     - **③ 語尾・終助詞・丁寧語終止形分割**: 句読点のない口語連続文に対し、終助詞（`〜わ`、`〜ね`、`〜よ`、`〜な`、`〜ぞ`、`〜じゃん`、`〜だし` 等）や丁寧語（`〜です`、`〜ます`、`〜でした`、`〜ました`）の直後で分割。
     - **④ 長文時（15〜20文字超）の文節拡張形態素分割**: SudachiPyを用いて、接続助詞（から、けど等）に加え、並列助詞（`〜て`、`〜で`、`〜し`）や連用形で安全に分割。
   - **音響パイプライン保護ガード**:
     - *オーバーセグメンテーション防止*: 各パーツ最低 5〜7 文字以上を担保し、細切れによるロボット声を防止。
     - *アンダーラン（音途切れ）防止*: 先頭チャンクが短すぎる場合の後続パーツとの安全マージ。
     - *自然な息継ぎポーズ*: 句点（150ms）とは異なり、スペース・終助詞は 60〜80ms の自然なブレスを設定。
2. **先頭チャンク最優先ディスパッチ**:
   - チャンク1（冒頭）は最短遅延のノードへ優先投入。先頭音声が届いた瞬間に Discord VC で即時再生開始。
3. **再生時間のタイムスリップ合成**:
   - チャンク1を再生している時間（約1〜2秒）の裏で、残りのチャンク2以降を各 Worker から非同期回収。
4. **投機的タイムアウト (400ms)**:
   - Worker にリクエスト後、400ms 以内に先頭フレームが来ない場合は、即座にクラウドTTS（Google/Edge）やローカル軽量エンジンへ並列横取りリクエストを発行。
5. **ノード全滅時のフォールバック保証**:
   - 指定エンジンを持つノードが全員オフライン・離脱時は、即座にクラウドTTSまたは標準ボイスへ自動フォールバックし、発話完遂を100%保証。

### 3.3 Worker層 (クライアントエージェント)
- **オンボーディング自動化 (ワンライナー)**:
  - **Windows (`setup-worker.ps1`)**:
    - Docker Desktop 有効時: Docker Compose バックグラウンド起動。
    - Docker 無効/一般PC時: ネイティブポータブル版（VOICEVOX Windows版 + Python Agent）を `%LOCALAPPDATA%\TTSBotWorker` に自動展開、タスクトレイ常駐・スタートアップ登録。
  - **Linux (`setup-worker.sh`)**:
    - Docker または systemd サービスとして自動登録・起動。
- **ゲーム検出 & 自動ポーズ**:
  - Steam / 主要ゲームプロセスの実行を検知した場合、自動で「離脱（Busy）」を Master に通知し、ゲームプレイを阻害しない。
  - タスクトレイアイコンから 1クリックで「1時間一時停止」が可能。
- **自動自己アップデート**:
  - 起動時および待機中に Master から最新スクリプトのハッシュを確認し、差分があれば自動更新・再起動。

### 3.4 テナンシー & ルーティング階層
```text
[発言受信]
   │
   ▼
【優先度 1: サーバー専用ノード】
   └─ そのDiscordサーバーに紐付けられたメンバーのPC
      │ (オフライン / ビジー時)
      ▼
【優先度 2: 全体共有プール】
   └─ 「他サーバー利用OK」としている余剰ノード
      │ (全ノード満杯 / オフライン時)
      ▼
【優先度 3: クラウド / ローカルフォールバック】
   └─ Google Cloud TTS, Edge-TTS, OpenJTalk 等
```

## 5. 着手タイミングと推奨手順

### なぜ「新環境への移行完了後」にKickすべきか
1. **変更スコープの分離**:
   - 現在進行中の旧環境 ➔ 新環境移行作業中に新アーキテクチャのコードを投入すると、障害発生時の原因切り分け（インフラ移行起因か、新機能コード起因か）が極めて難しくなります。
2. **基盤の安定確認**:
   - まず新環境で従来の単一Master/Worker構成が100%安定稼働することを確認してから着手することで、手戻りなく安全にフェーズ1から段階展開できます。

### 移行完了後のKick手順
1. 新環境でのサービス稼働・動作確認完了
2. フェーズ 1（WebSocket Gateway & Worker Agent プロトタイプ）を非破壊ブランチで開始
3. サンドボックス検証環境でプロトコル疎通テスト
4. 順次フェーズ 2〜5 へ展開
