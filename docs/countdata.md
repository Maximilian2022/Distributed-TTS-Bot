## 1. エグゼクティブサマリー

本番環境でユーザーから依頼される「1回の発話（メッセージ）あたりの文字数」を集計した結果、**約73.5%が15文字以下、92.2%が25文字以下の短文**であることが判明しました。

| 指標 | 数値 | 詳細・根拠 |
| :--- | :--- | :--- |
| **中央値 (Median)** | **10.0 文字** | 全発話のちょうど中央に位置する値（数学的に確定） |
| **最頻値 (Mode)** | **7 文字** | 最も頻出する文字数（338回 / 全体の 6.8%） |
| **平均値 (Mean)** | **約 12.5 文字** | 全体平均推定値（推定範囲: 12.1 〜 13.4 文字） |
| **25文字以下の割合** | **92.2%** | 全4,989件中 4,599件が25文字以下 |
| **26文字以上の割合** | **7.8%** | 長文は全体の1割未満 |

## 5. 文字分割・ストリーミング処理への技術的示唆

本集計結果を踏まえ、現在の文字分割機構（`TextCleaner.split_into_chunks`）および再生パイプラインに対して以下の最適化が有効であると考えられます。

### ① 20〜25文字以下の「形態素解析ファストパス（完全スキップ）」
- **根拠**: 発話の9割以上（92.2%）が25文字以下。
- **課題**: 過去の遅延インシデントで、SudachiPy/Janome の呼び出しやロック待ちによる `TEXT_SPLIT_OVERHEAD`（2〜7秒遅延）が発生していた。
- **改善案**: 本文が25文字以下の場合は、重い形態素解析エンジンを通さず即座に分割完了とするガードを設ける。これにより、全リクエストの9割以上で文分割処理時間を 0.1ms 未満に短縮可能。

### ② 短文（15文字以下）の過剰分割防止
- **根拠**: 発話の約73.5%が15文字以下。
- **課題**: 「スペース」「笑い」「語尾」などの閾値が下がりすぎると、6〜8文字の短文が「3文字＋4文字」のように過剰に細切れになり、イントネーションの破綻やTTSリクエストの増加を招く。
- **改善案**: 本文が15文字以下の場合は無理に文節分割せず、1チャンク（全文一括）で合成する。名前プレフィックス再生時間（約0.8〜1.0秒）の間に15文字は余裕を持って合成完了できる（クラウドTTSなら200〜400ms）。

### ③ 「短文ストレートパス」と「長文ストリーミング」の2段構え化
- **根拠**: 26文字以上の長文は全体のわずか 7.8%。
- **改善案**: 全件に対して高度な動的短縮やタイムライン予測を常時計算するのではなく、25文字以下は「超高速ストレートパス」、26文字以上のみ「長文ストリーミングパイプライン」を適用する二段構えの構成にすることで、日常会話のオーバーヘッドを極小化する。
